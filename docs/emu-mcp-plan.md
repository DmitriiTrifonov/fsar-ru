# План: управляемый эмулятор DS для Claude Code (MCP)

Дата: 2026-10-17. Статус: только план, ничего не установлено и не запущено.
Цель: загружать сейвстейт, жать кнопки DS, ускорять, снимать верхний и нижний экран, читать память, чтобы быстро проверять русский текст в поздних главах без ручного прохождения.

## 1. Краткий вывод

Рекомендую **не управлять GUI-melonDS снаружи**, а собрать **собственный безголовый драйвер на ядре melonDS 1.1** (статическая библиотека `core` из того же репозитория, без Qt и без окна) и обернуть его в MCP-сервер на Python.

Почему:
- Ядро то же, что в `/Applications/melonDS.app` (1.1), поэтому точность эмуляции та же и **текущие `.ml1`, скорее всего, загружаются как есть** (формат и функции `DoSavestate` общие; проверить на этапе 1).
- Управление полное и надёжное: кнопки, касание, сейвстейты, пошаговый запуск кадров, скорость без ограничений (сотни кадров в секунду), чтение памяти шины ARM9/ARM7, оба экрана как массивы пикселей.
- Не нужны разрешения macOS (ни Accessibility, ни Screen Recording), окно не появляется и не мешает работе пользователя.
- Не нужно ставить Qt (около 1–2 ГБ). По CMake ядро (`add_library(core STATIC ...)` в `src/CMakeLists.txt`) от Qt не зависит; в `cmake`/`ninja`/Xcode CLT на машине всё нужное для сборки уже есть.

Запасные пути (по убыванию предпочтения):
1. **Патч Qt-фронтенда melonDS** (добавить сокет управления) — если нужно видеть живое окно; дороже (Qt6 через brew).
2. **Внешнее управление текущим melonDS** через CGEvent + `screencapture -l` — ничего не ставить, но хрупко и требует разрешений.
3. **py-desmume** (DeSmuME как Python-библиотека) — быстрый независимый пробник, но другой эмулятор и свои сейвстейты.
4. RetroArch + ядро melondsds и готовый `mcp-retroarch` — не рекомендую (см. таблицу).

## 3. Результаты исследования вариантов

### (a) Готовые MCP-серверы для эмуляторов
- **mcp-retroarch** (TypeScript, dmang-dev; и Python-переписка pythoninthegrass, MIT, 14 коммитов, 0 звёзд, релизов нет, «очень ранняя стадия»). Работает через RetroArch Network Control Interface (UDP 55355): ping/status, чтение/запись памяти (карта памяти libretro и CHEEVOS), пауза/кадр/сброс, скриншот (в папку RetroArch, не возвращается как картинка), сейвстейты (только текущий слот, загрузка по слоту есть). **Ввод кнопок через NCI невозможен** (NCI знает только хоткеи и меню); Python-версия шлёт кнопки по UDP «Network RetroPad» (порт 55400+N), для этого в RetroArch нужно вручную назначить игроку драйвер Network Retropad; формат пакетов не документирован, UDP без гарантий доставки.
- **mcp-bizhawk**: в списке систем нет DS; официальный BizHawk на macOS не поддерживается (нужна VM или старая 1.x-сборка Sappharad). Не подходит.
- Готового MCP/CLI-сервера для melonDS или DS-ядра я не нашёл.

### (b) RetroArch + libretro melondsds (JesseTG)
- Поддерживает macOS (x86_64 и arm64); ядро по состоянию на сейчас в Steam-RetroArch отсутствует, его надо ставить вручную (`melondsds_libretro.dylib` + `.info`) или из Core Downloader в обычной (не Steam) сборке.
- Сейвстейты есть (кроме homebrew и DSi); **совместимость с `.ml1` стандартного melonDS нигде не заявлена**, формат libretro-состояний другой, текущие `.ml1` почти наверняка не подойдут.
- Нет GDB-стаба (в README «not yet»). Чтение памяти через NCI возможно только если ядро отдаёт карту памяти (в README не упомянуто — проверять).
- Ввод: только через Network Retropad (см. выше), обязательная ручная настройка.
- Оба экрана: скриншот RetroArch делает один кадр с раскладкой ядра; раздельные экраны получить сложнее.
- Вывод: много чужих слоёв (RetroArch, NCI, UDP-геймпад, неподдерживаемое MCP-обёртка), при этом сейвстейты придётся пересоздавать. Риск высокий, выигрыш малый.

### (c) DeSmuME
- Актуальная версия 0.9.13 (на macOS есть через Homebrew cask, выпуск из TASEmulators). Lua-движок появился в 0.9.5 в Windows-порте; **на macOS Lua в сборке не подтверждён** (не нашёл).
- Для автоматизации лучше библиотека **py-desmume** (SkyTemple, GPL-3.0): классы `DeSmuME`, `DeSmuME_Input` (`add_key/rm_key/keymask`), `DeSmuME_Savestate`, `DeSmuME_Memory`, метод скриншота. На PyPI последняя версия 0.0.9; колёса macOS в видимой части списка — `macosx_11_0_universal2` и `x86_64` для старых версий, для 0.0.9 не проверено, без колеса сборка из исходников (`brew install sdl2 meson glib gcc`). Безоконный режим в документации не описан (есть `DeSmuME_SDL_Window`, значит окно отдельно).
- Сейвстейты DeSmuME (`.dst`) несовместимы с `.ml1`. Эмуляция другого ядра: расхождения с melonDS возможны, а мы уже проверяли шрифты и окно диалога именно в melonDS (ширина 194 px и т. д.), так что любые расхождения в отрисовке надо перепроверять.
- Вывод: хороший запасной пробник «за вечер», не основной путь.

### (d) Управление самим melonDS 1.x
- Командная строка (`src/frontend/qt_sdl/CLI.cpp`): только `-b/--boot`, `-f/--fullscreen`, `-a/-A` (архивы) и пути к ромам. Ни IPC, ни Lua, ни безоконного режима, ни ввода, ни сейвстейтов по команде. Официальные релизы: 1.0 (2025-07-08), 1.1 (2025-11-18); по сторонним данным активные коммиты продолжаются в 2026, тега 1.2 не нашёл.
- Готовых форков с Lua/сервером управления не нашёл (Lua для DS есть только у BizHawk-ядра melonDS и DeSmuME).
- Устройство кода, полезное для патча/своего драйвера (по исходникам на GitHub, ветка master, может отличаться от тега 1.1, проверить):
  - `EmuInstanceInput.cpp`: маска кнопок активна-низкая (`keyInputMask`, бит 0 = A … бит 11 = Y, 0xFFF = всё отпущено), касание `touchScreen(x,y)` / `releaseScreen()`; поля обычные `int`/`bool`, не атомарные.
  - `EmuThread.cpp`: очередь сообщений `sendMessage/waitMessage` между UI и потоком эмуляции; `saveState(filename)`, `loadState(filename)`, `undoStateLoad()`; хоткеи Pause, FrameStep, FastForward, Reset.
  - `EmuInstance.cpp`: имя состояния `<имя рома>.ml<слот>` (в `SavestatePath` или рядом с ромом), `nds->DoSavestate(&state)`.
  - Ядро: `core` как `STATIC`-библиотека без Qt; сборка Qt-фронтенда по BUILD.md требует `qt@6 sdl2 libarchive enet zstd faad2 pkg-config`.
- В ядре есть и GDB-стаб (уже используется), и (по меню GUI) «RAM search», то есть чтение памяти встроено.
- Лицензия GPL-3.0: для личного использования патчи и свой драйвер допустимы, ром и бинарники не распространяем.

### (e) Внешнее управление GUI-melonDS на macOS
- Нажатия: `CGEventPostToPid` (Quartz, через Swift или `pyobjc`) шлёт события процессу в обход фокуса, но на практике есть сообщения, что это работает не для всех приложений, поэтому для Qt-окна нужно тестировать. Нужно разрешение **Accessibility** для приложения, которое шлёт события (Terminal/iTerm/ghostty). Иначе событие уходит только в активное приложение (`osascript`/`cliclick`), то есть отбирает у пользователя клавиатуру.
- Скриншот окна: `screencapture -x -o -l <id>` (уже используется; нужно **Screen Recording**). Окно включает рамки и меню, оба экрана в одной картинке; для точных пикселей придётся вырезать и масштабировать вручную.
- Загрузка сейвстейта: только через меню/горячие клавиши melonDS (по памяти F1..F8 / Shift+F1..F8, **проверить** в конфиге/меню), то есть опять синтетические клавиши. Ускорение: зажать Tab (в конфиге это FastForward).
- Нет чтения памяти по запросу, кроме GDB (с остановкой эмулятора и правилами из AGENTS.md) и анализа сейвстейтов.
- Вывод: нулевые установки, но самая хрупкая и самая мешающая вариация.

## 5. Рекомендуемый путь и поэтапный план

Архитектура:
```
Claude Code ──MCP(stdio)──> scripts/emu_mcp.py (Python, tools/venv + пакет mcp)
                              │  JSON-строки по stdin/stdout (или unix-сокет)
                              ▼
                       tools/melonds-ctl  (C++17, линкуется с core из melonDS 1.1)
                              │
                       ром build/fsar-test.nds, состояния *.ml1, .sav
```
Исходники melonDS клонируем **вне проекта** (например `~/Developer/tools/melonDS`, тег `1.1`), в проект кладём только `tools/melonds-ctl/` (наш `main.cpp` + `CMakeLists.txt`) и собранный бинарь. Ром, дампы и бинарники не пушим и не кладём в хранилище.

### Этап 0. Разведка совместимости (30–60 мин, ничего не ставим)
- Проверить на тег `1.1`: `git clone --branch 1.1 https://github.com/melonDS-emu/melonDS` (нужно разрешение на сеть и каталог), посмотреть `src/NDS.h` (`NDSArgs`, `RunFrame`, `SetKeyMask`, `TouchScreen`, `ReleaseScreen`), `src/GPU.h` (`GetFramebuffers`), `src/Savestate.h`, `src/frontend/qt_sdl/EmuInstance.cpp` (как создаётся `NDS`, как грузятся BIOS/firmware freebios и как кладётся ром).
- Проверка успеха: найдены все семь вызовов; в `src/CMakeLists.txt` понятно, нужны ли `zstd`/`enet`/`libarchive` для цели `core` (по документации нет, но Teakra берётся из подпапки).
- Заодно (без запуска): записать, какие настройки влияют на состояние: DirectBoot, freebios, язык 1, имя «melonDS», дата/время (RTC).

### Этап 1. Сборка безголового драйвера (3–5 ч)
- `tools/melonds-ctl/main.cpp`: создать `melonDS::NDS` с теми же настройками, что в `melonDS.toml` (DirectBoot, встроенные BIOS/прошивка, язык 1, программный рендер, JIT выключен), загрузить ром и `.sav`, REPL на JSON-строках с командами из раздела 6.
- Сборка: `cmake -S ~/Developer/tools/melonDS -B build -DBUILD_QT_SDL=OFF -DENABLE_OGLRENDERER=OFF` для `core`, затем наш бинарь отдельным CMake-проектом, который подключает `core`.
- Проверка этапа: 
  1. `echo '{"cmd":"load_rom","path":".../build/fsar-test.nds"}' | tools/melonds-ctl` — ром запускается, `run_frames 600`, `screenshot` отдаёт PNG титульного экрана (сверить с известным титульным экраном и кириллицей из `patched_raw`).
  2. **`load_state tools/rebuilt.ml1`** (копию, чтобы не затирать) с `rebuilt.nds`: скриншот должен совпадать с тем, что видно в melonDS при загрузке этого состояния (тот же кадр), а реплика «I'm Sumio Mondo.» находиться через `find_text` по адресу `0x022EE754`, как в AGENTS.md. Это главная проверка точности и совместимости состояний.
  3. `run_frames` без лимита: скорость ≥ 300 кадров/с при сборке `Release`.
- Если `.ml1` из GUI не грузится (например, различие версий или настроек): запасной ход — сделать состояния заново уже драйвером (этап 3), совместимость с GUI не критична.

### Этап 2. MCP-сервер (2–3 ч)
- `scripts/emu_mcp.py` на пакете `mcp` (FastMCP) в `tools/venv`: запускает `melonds-ctl` подпроцессом, отдаёт инструменты из раздела 6. Скриншоты возвращаются как image content (PNG, по умолчанию масштаб 2×).
- Регистрация: `claude mcp add fsar-emu -- ~/Developer/games/fsar-ru/tools/venv/bin/python -I ~/Developer/games/fsar-ru/scripts/emu_mcp.py` (область `project`, `.mcp.json` в корне; файл проекта меняем только с вашего согласия).
- Проверка этапа: в новой сессии Claude вызывает `emu_open`, `load_state`, `screenshot`, `press A`, `screenshot` и видит продвижение реплики.

### Этап 3. Сцены и сейвстейты для поздних глав (3–6 ч, зависит от игры)
Главная проблема — не инструмент, а **как попасть в нужную сцену**:
- Сейвстейт хранит уже загруженный в RAM скрипт сцены (AGENTS.md: «показывает старый текст»). Поэтому состояния для проверки перевода надо делать **до** загрузки сцены, а скрипт подставится уже из рома при входе в сцену. Это работает только если файлы рома читаются заново из нового рома.
- **Риск смещений:** ром, собранный `ndstool -c`, при пересборке меняет размеры сжатых `.z` и смещения; в состоянии может быть закэширована таблица файлов/адреса. Проверка: взять состояние с `build A`, пересобрать ром с другим текстом (`build B`), загрузить состояние на `B` и пройти вперёд до чтения нового файла. Если ломается, варианты: (1) держать постоянную раскладку файлов (дополнять пересжатые `.z` до исходного размера, если влезают); (2) записывать **макросы ввода** (последовательность `press`/`wait_frames` от New Game/главы) и воспроизводить их на каждом билде; (3) делать состояния заново на каждом билде автоматически.
- Выяснить, есть ли в игре выбор главы/быстрый переход (в `Chapter/Pack/Cxx` есть главы; ручной выбор — вопрос к пользователю/эксперименту). Если нет, пригодится запись макросов ввода, ускоренное пролистывание диалогов (удержание A на высокой скорости) и состояние на входе в каждую главу.
- Опционально: найти в RAM переменную «текущая сцена» и менять её через `write_mem` (потребует реверса, оценка 1+ день, делать только если макросы не хватит).
- Проверка этапа: для 3 разных глав (например C01, C09, C18) команда `goto_scene` (макрос или состояние) приводит к скриншоту нужной реплики на русском.

### Этап 4. Удобства под задачу русификатора (2–4 ч)
- `check_dialog(id)`: макрос «дойти до реплики», скриншот, сравнение ширины (дополняет `scripts/check_table.py`).
- `find_text(text)`: поиск строки UTF-16LE в RAM (как `scripts/find_in_state.py`, но по живой памяти).
- Пакетный прогон: список (глава, шаги) → папка `dumps/shots/…` и контактный лист.
- Сохранение «золотых» состояний в `dumps/states/` (вне git/хранилища, не публиковать).

### Оценка времени
Минимум рабочий инструмент (этапы 0–2): около 1–1,5 дня работы Claude с вашими разрешениями. С поздними главами (этапы 3–4): ещё около 1 дня. Основная неопределённость — этап 3 (смещения файлов и вход в сцены).

## 6. Предлагаемый интерфейс MCP-инструментов

Все инструменты возвращают JSON `{ok, frame, ...}`; скриншоты — как изображения плюс путь файла.

| Инструмент | Аргументы | Что делает |
|---|---|---|
| `emu_open` | `rom` (по умолчанию `build/fsar-test.nds`), `sav` (необяз.), `reset` (bool) | Создать/пересоздать эмулятор, загрузить ром и `.sav` |
| `reload_rom` | `rom` | Подгрузить заново пересобранный ром, сохраняя `.sav` |
| `reset` | – | Сброс консоли |
| `load_state` | `path` (файл `.ml1` или имя слота) | Загрузить состояние |
| `save_state` | `path` | Сохранить состояние |
| `press` | `keys` (`A B X Y L R Start Select Up Down Left Right`), `hold` (кадры, по умолчанию 3), `then_wait` (кадры) | Нажать и отпустить |
| `hold` / `release` | `keys` | Удерживать и отпустить кнопки |
| `touch` | `x`, `y` (0–255, 0–191 нижнего экрана), `hold` | Касание стилусом |
| `input_sequence` | `steps`: `[{keys, hold, wait}]`, `repeat` | Макрос ввода (пролистывание диалога, меню) |
| `wait_frames` | `n` | Прогнать N кадров без ввода |
| `run_until` | `cond`: `screen_stable` \| `mem_eq` \| `mem_changed` \| `text_in_ram`, `max_frames` | Ждать условия (например, окончания вывода реплики) |
| `set_speed` | `mode`: `max` \| `realtime`, `limit_fps` | Скорость (в безголовом режиме по умолчанию без лимита) |
| `screenshot` | `screen`: `top` \| `bottom` \| `both`, `scale` (1–4), `save_as` | PNG экранов, раскладка `both` вертикальная |
| `read_mem` | `addr`, `len`, `cpu` (`arm9`\|`arm7`), `fmt` (`hex`\|`u8/u16/u32`\|`utf16le`) | Чтение шины |
| `write_mem` | `addr`, `data`, `cpu` | Запись (для отладки, по явной просьбе) |
| `find_text` | `text`, `encoding` (utf16le по умолчанию), `limit` | Поиск строки в основной RAM |
| `get_status` | – | Кадр, режим, загруженный ром, активные кнопки |
| `goto_scene` (этап 3) | `chapter`, `scene` или `state` | Попасть в сцену по макросу/состоянию |

## 7. Что понадобится от пользователя

Для основного пути (A):
1. Разрешить `git clone` исходников melonDS (тег `1.1`) в каталог вне проекта, например `~/Developer/tools/melonDS`, и сборку через `cmake`/`ninja` (около 5–10 минут, нужен интернет только для клонирования).
2. Разрешить установку Python-пакета `mcp` в `tools/venv` (`pip`, нужен интернет).
3. Разрешить `claude mcp add` (проектный `.mcp.json`) и перезапуск Claude Code, чтобы инструменты появились.
4. Ответить на вопросы по игре: есть ли выбор главы или быстрый переход; можно ли для начала сделать несколько состояний-«вех» (вход в главы) через GUI-melonDS до загрузки сцены (слоты `.ml2…`).
5. Brew-установки и разрешения macOS (Accessibility, Screen Recording) **не нужны**.

Для запасных путей:
- B: `brew install qt@6 sdl2 libarchive enet zstd faad2 pkg-config` (порядка 1–2 ГБ, новые пакеты в системе).
- C: разрешения «Универсальный доступ» и «Запись экрана» для терминала; `brew install cliclick` по желанию.
- D: `pip install py-desmume` в отдельный venv (при отсутствии колеса — `brew install sdl2 meson glib gcc`).
- E: установка ядра melondsds и включение Network Commands/Network Retropad в RetroArch.

## 8. Риски и митигации

| Риск | Вероятность | Митигация |
|---|---|---|
| API ядра 1.1 отличается от `master` (имена `NDSArgs`, `GetFramebuffers`) | средняя | Работать строго с тегом `1.1`; в этапе 0 сверить сигнатуры |
| `.ml1` из GUI не грузятся в драйвере (разные настройки) | низкая-средняя | Повторить настройки из `melonDS.toml`; запасной вариант — состояния, созданные самим драйвером |
| Состояния привязаны к раскладке файлов старого рома | средняя-высокая | Проверка в этапе 3; макросы ввода или постоянная раскладка файлов |
| Отрисовка программного рендера отличается от OpenGL в GUI | низкая (2D-текст идентичен) | Сравнить скриншот с GUI на одном состоянии |
| Нет доступа к недостающим прошивкам/BIOS | низкая | Как и в GUI, используем freebios |
| Время на вход в сцену превышает выгоду | средняя | Начать с 3–5 «золотых» состояний по главам; макросы только для самых нужных сцен |
| Лицензия GPL-3.0 | – | Не распространять бинарь; личное использование |
| Обновление macOS/Xcode ломает сборку | низкая | Зафиксировать тег, собирать локально |

## 9. Запасной план по шагам

- **Быстрый старт без сборки (C):** `scripts/melon_press.swift` (CGEventPostToPid + проверка Accessibility), `scripts/melon_shot.sh` (`screencapture -l` + кроп двух экранов), MCP-обёртка с `press`, `screenshot`, `load_state` (через горячие клавиши) и `fast_forward` (удержание Tab). Проверка: после `emu_open` вручную запущенного окна `press A` продвигает реплику, не отбирая клавиатуру (проверить, что активное приложение не меняется); если событие требует фокуса, вариант нежизнеспособен.
- **Патч Qt (B):** взять наработки этапа 1 как справочник; добавить в `EmuThread` приём команд через `QLocalServer`/TCP на `127.0.0.1`, вызывать `emuInstance->onKeyPress/onKeyRelease/touchScreen`, `saveState/loadState`; скриншоты через `GPU::GetFramebuffers`. Оценка 2–3 дня.
- **py-desmume (D):** `pip install py-desmume` в временный venv, проверка: загрузка рома, 60 кадров, скриншот, `memory.unsigned`. Использовать только для сверки, если драйвер A покажет расхождения.

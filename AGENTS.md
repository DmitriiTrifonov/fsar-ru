## Формат скрипта
- Диалоги: `Chapter/Pack/Cxx/<ue|fr|de|es|it>/Cxx_yy.s.z`, LZ10, UTF-16LE с BOM, переводы строк CRLF.
- Реплика: строка `[[ID`, затем текст; `<R>` на отдельной строке — перенос внутри окна; строки с `//` — комментарии разработчиков.
- Сцена `Cxx_yy.txt` (общая для языков) вызывает реплики через `<TEXT_EX>ID</TEXT_EX>`; говорящий — первое число в ближайшем `<SETFACE2>` перед ней.
- Разбор `.s` → сборка даёт побитово тот же файл на всех 3198 файлах. Пересжатие LZ10 даёт те же данные для 4317 текстовых `.z`, но не всегда те же байты.
- Побитово собранный `ndstool -c` ром не совпадает с оригиналом (другие смещения, обрезан хвост), содержимое файлов при повторной распаковке идентично.

## Живая отладка (melonDS 1.1 + GDB)
melonDS: Config → Emulation settings → Devtools → включить GDB stub. Порты: ARM9 `3333`, ARM7 `3334`. Включать стаб и запускать игру должен пользователь.

Пока GDB подключён, эмулятор стоит. Правила:
1. Не подключаться к эмулятору без явной команды пользователя («ром запущен, стаб включён»).
2. Одно подключение на сеанс, всегда заканчивать `detach`. Не оборачивать клиент в `timeout`: оборванная сессия оставляет стаб зависшим, лечится выключением/включением GDB stub и Reset в melonDS.
3. Запускать долгие команды в фоне (`run_in_background`) и ставить `set remotetimeout 60`.
4. Брейкпоинты и вочпойнты — только по явной просьбе, снимать перед `detach`.

Дамп основной RAM через GDB (4 МБ) ненадёжен: дважды зависал, зависший клиент держит эмулятор остановленным. Если всё же нужен, читать кусками по 64 КБ (`dump binary memory` на диапазоне) и запускать в фоне. Для поиска данных предпочитать сейвстейты.

## Сейвстейты (основной способ анализа памяти)
- Пользователь сохраняет состояние в melonDS (слот N). Файл `<имя рома>.mlN` лежит рядом с ромом, с которого запущена игра (сейчас `tools/rebuilt.ml1` от `tools/rebuilt.nds`). Если не найден: `find` по `~/Library/Application Support ~/Documents ~/Downloads ~/Desktop ~/Developer/games -maxdepth 5 -name '*.ml?'`.
- Формат несжатый: заголовок `MELN`, секция `NDSG` с 0x10. Основная RAM ARM9 начинается со смещения файла 0x24: адрес ARM9 = смещение файла + 0x01FFFFDC (сверено с GDB-дампом: «OK, I'll make this quick.» по 0x022EE708 ↔ смещение 0x2EE72C).
- Новый ром — новые слоты: сейвстейт ищется как `<имя рома>.mlN` рядом с ромом. После каждой сборки `fsar-gfxN.nds` сразу копировать опорные состояния из `states/` (`katharine-first-connect.ml1` → слот 1, `hotel-start.ml2` → слот 2) в `build/fsar-gfxN.ml1|ml2`, до перезапуска эмулятора. Состояния привязаны к спрайтам старого рома (подмена: `patch_state_gfx.py`); страницы Guide/LostList в них не резидентны, подхватываются из нового рома.
- **Раскладка рома должна не меняться между сборками, пока живы сейвстейты.** Состояние хранит таблицу файлов рома, на котором снято: если стартовое смещение любого файла сдвинулось (файл вырос за границу 512-байтового блока), состояние виснет на чёрном экране. Проверка: сравнить FAT двух ромов (смещения начала файлов в `header[0x48]`), отличаться могут только концы файлов. `build_rom.py` сам дополняет нулями файлы, ставшие меньше, до размеров рома из `build/layout.json` (создаётся `scripts/layout_lock.py --make <ром, на котором сняты состояния>`); при росте файла печатает WARNING. Если страница выросла, сжать её `lz10.compress_opt` (оптимальный разбор, 2–5 % меньше) и добавить имя в `SLOT` в `scripts/gfx_lost.py`.
- Поиск реплик: `LIMIT=4400000 EN_ONLY=1 python3 -I scripts/find_in_state.py <файл.ml1> 0 50` (строки таблицы как UTF-16LE). Без `LIMIT`/`EN_ONLY` на 19 МБ работает слишком долго.
- Пример: на слот 1 реплика «I'm Sumio Mondo.» (C00_01, ID 01002) найдена по смещению файла 0x2ee778 (адрес 0x022EE754); скрипт сцены целиком загружен с адреса 0x022EE708, ещё одна копия строк около смещения 0x2f04a0.

## TAS-макросы и быстрый доступ к главам (2026-10-18)
- Плеер: `tools/venv/bin/python -I scripts/tas.py <rom> macros/<имя>.txt [--sav файл.sav] [--save-dir DIR] [--set N=4]` (команды: `wait`, `press`, `mash`, `touch`, `wait_pixel`, `wait_change`, `checkpoint`, `shot`, `request N`, `raw`; список в докстринге). Чекпоинт = обычный сейвстейт melonDS (`dumps/emu/cp_<имя>.ml1`) + `cp_<имя>.png`. Два прогона дают побайтово одинаковые чекпоинты.
- ВНИМАНИЕ: в драйвере `keys <hex>` — маска НАЖАТЫХ кнопок, `keys 0` отпускает всё; `keys 0xFFF` зажимает все 12 кнопок (из-за этого раньше ломались мои скрипты). Через `emu_press` и `tas.py press` всё правильно.
- `macros/intro.txt`: с нуля до первой сцены (`drive_scene`, `first_dialogue`). `macros/to_request.txt --set N=4`: загрузить Data-01 из сохранения с пройденной игрой, открыть «Заказ» у Эдо и запустить R-04; на любой главе (R-00…R-18).
- Сохранение с пройденными главами: `fsar-eu-100pct.sav` (чужой файл, 64 КБ, «Flower_Sun_Rain», слоты Data-01 и Data-03, «055% завершены»), лежит в `build/full/` (в git не входит). Использовать как `--sav build/full/<rom>.sav`; ваш `build/<rom>.sav` не трогать.
- `states/requests/cp_request_N.ml1` (N=0..18, не в git) — состояния на старте каждого заказа (рома gfx16); `macros/walk_request.txt --set N=1` проигрывает диалог от такого состояния, жмёт A и снимает кадр после каждой реплики (`dumps/emu/walk/rN_000.png…`); из кадров собирается контактный лист для вычитки в игре.
- Меню Эдо (кнопки): Начать игру → слот → Загрузка → «Продолжить / След. дни / Заказ / Настройки / Назад»; «Заказ» → список R-00… по 3 на странице, «Далее» листает, первое касание выбирает, второе подтверждает.

## Графика (`.pbg`, `.pobj`)
- Формат: контейнер `D2KP` (0x58 байт заголовка; размеры секций в двойных словах 6, 7, 12 = `(размер+4)&~3`) + стандартные NCLR/NCGR/NCSR (`.pbg`) либо NCLR/NCGR/NCER/NANR (`.pobj`, пока без обратной упаковки). Смещение данных в блоках NCGR/NCLR считается от конца 8-байтового заголовка блока.
- Страницы `Guide/ue`, `LostList/ue` (длинные ленты): один тайл на ячейку, карта экрана хранит только 10 бит номера и «заворачивается» после 1024, поэтому тайл `i` = ячейка `i` (`info["identity"]`), предела тайлов нет. Остальные (`2D/ue`, логотипы): карта с повторами тайлов (и отражениями), предел 1024 тайла.
- `scripts/ds_gfx.py`: `parse`, `decode_indexed` (индексы палитры, у 4 bpp `банк*16+цвет`), `render_screen`, `repack(d, info, rows)` (обратная упаковка; неизменённые ячейки не трогаются, картинка без правок упаковывается побайтово). `scripts/gfx_export.py <папка> <куда>` — PNG и контактные листы, `scripts/test_gfx.py` — проверка (671 файл без правок побайтово; правки декодируются обратно).
- Редактирование: брать `decode_indexed`, менять индексы палитры, `repack`; у 4 bpp все пиксели одной ячейки 8×8 должны быть из одного банка палитры по 16 цветов. Текст страниц `Guide/ue` и `LostList/ue` нарисован НЕ шрифтами из файлов игры (см. ниже): 1 бит на пиксель, ascender 8 строк, x-height 6, шаг строк 11 px, буквы касаются друг друга (нет пустых столбцов между ними), поэтому нарезка по столбцам даёт слипшиеся пары (`th`, `re`, `fo`…), `scripts/gfx_atlas.py <куда> <папки .pbg>` строит атлас таких фрагментов (1603 разных на 70 страницах, 36842 всего).
- **Проверка в игре по шагам — `docs/verify-in-game.md`** (сборка рома и раскладка, диалоги глав через TAS и контактные листы, Guide, LostList, подводные камни драйвера). Читать перед любой проверкой в эмуляторе.

## Окно диалога: размеры и правила (измерено в melonDS 2026-10-15)
- Игра НЕ переносит слова и не обрезает аккуратно: лишнее рисуется поверх портрета и уходит за край экрана, остаток теряется. Строки разбиваем вручную (`<R>` в `.s`, `\n` в ячейке таблицы).
- Ширина строки считается как сумма (advance + 1) по символам, у последнего считается ширина чернил (`scripts/linewidth.py`; проверено: 28×«н» = 194 px, в игре 193,8). **Безопасный предел 188 px** (с 2026-10-26; раньше 194). Окно с портретом СЛЕВА (Мондо и почти все лица в проверенных сценах) начинает текст с x=58, а правее x≈245 игра обрезает чернила: «отличный.» на 194 px показывается как «отличны» + срез буквы (в melonDS и в рекомпе одинаково). Раскладка в движке одна: портрет слева, рамка x=48, текст с x=58 (разработчик рекомпа, 2026-10-26: ни лицо, ни `SETFACE2`, ни сцена сторону не меняют). Правый портрет (текст от x=10, граница x≈207) есть только на кадрах ранних сборок 17–18 октября (`dumps/shots/c00_a.png`, `dumps/emu/u4…g13`): отсюда был ошибочный предел 194. Разработчик называет реальную границу около 185 px, у нас строки 186–188 видны целиком (чернила до x≈245–246), но у самой звезды F.S.R.; решение пользователя 2026-10-26: оставить 188. `scripts/rewrap188.py` переразбивает строки шире лимита (только переносы), `check_table.py` и `tr_bulk.py` теперь тоже считают по 188.
- Не больше 3 строк на реплику: 4-я прокручивает окно, первая строка пропадает. Если не влезает, разбить реплику.
- Английский оригинал: 99% строк не шире 158 px, медиана 107, max 264 (21 строка шире 204 в эпилоге `C18_24` и у Кантоны, вероятно другие окна). Русский длиннее на 15–30%.
- Проверка таблицы: `python3 -I scripts/check_table.py [--csv ...] [--col Русский]` (ширина, число строк, символы, которых нет в шрифте).

## Правила
- Побитово проверять цикл «разобрать → собрать» перед любым изменением формата вставки.
- Дамп рома и сгенерированные файлы не пушить и не класть в хранилище.

## Git и перевод
- Локальный git-репозиторий (удалённого нет). Оригинальные тексты игры в историю попадать не должны: `text/dialogue.csv` (полная таблица с JA/EN/…), `decoded/`, ром и всё производное — в `.gitignore`.
- В git лежит перевод: `text/ru.csv` (Глава, Сцена, ID, Русский) и черновики `text/ru/*.txt`. `set_ru.py`/`set_ru_files.py` после записи сами делают `ru_sync.py export`. Восстановление на новой машине: `make_table.py` (берёт русский из `text/ru.csv`) или `ru_sync.py import`.
- Коммитить после каждой порции перевода.

## Показ диалога пользователю
Когда пользователь просит показать сцену или реплики таблицей, колонки: ID, персонаж (говорящий), English, Русский. Говорящих даёт `scripts/dump_scene.py Cxx` (номер лица → имя, см. `text/STYLE.md`). Японский добавлять только по просьбе или для спорного места, изменённую реплику выделять жирным.

## Правка перевода: везде сразу (2026-10-24)
Источник правды — `text/ru.csv` (в нём ручные переносы). Черновики `text/ru/Cxx.tr` только следуют за ним: `ru_sync.py export` и `import` сами подтягивают в `.tr` изменённые реплики (`ru_sync.py tr`; `ru_sync.py check` показывает расхождения, ничего не меняя). Править реплику так: `python3 -I scripts/ru_set.py <Глава> <Сцена> <ID> "<текст>"` (`\n` — перенос) или `set_ru.py`/`set_ru_files.py`; все три обновляют `dialogue.csv`, `ru.csv` и `.tr`. Не править `.tr` руками отдельно и не загружать из `.tr` без `check`: `tr_bulk.py` перераспределяет переносы и затирает правки таблицы, если `.tr` отстаёт (так на C04 однажды слетели 52 реплики). После правки текста — `insert.py`, ром только по команде.

## Что изменено в переводе: `scripts/ru_changes.py`
Список изменённых реплик между двумя ревизиями `text/ru.csv` по ключу (Глава, Сцена, ID): `tools/venv/bin/python -I scripts/ru_changes.py [от] [до] [--md|--ids]`. По умолчанию «от» = последний локальный тег (`v0.1.1-alpha` стоит на коммите сборки релиза), «до» = рабочая копия; ревизия — тег, хеш, `HEAD~5`. `--md` даёт строки Markdown-таблицы «Глава | Сцена | ID | было | стало» (для заметок к релизу), `--ids` — сводку по сценам. Отдельного журнала правок не ведём: сообщение коммита называет сцену и ID, остальное восстанавливает скрипт. Картинки (Guide/LostList) скрипт не видит, их правки смотреть `git diff <тег> -- text/gfx`. После выпуска релиза поставить новый тег на коммит сборки: `git tag vX <коммит>`.
